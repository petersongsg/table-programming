# 表格编程 — 完整开发纲领

> 本文档为整套框架的**唯一权威纲领**,所有项目迭代、新增功能、Bug 修复、人员交接均严格遵照本文档执行。
> **核心定位**:代码只做固定载体,业务全部配置化,逻辑只读规则表即可读懂整机程序。

---

## 0. 文档说明

本文档整合全部架构思想、文件规范、线程模型、读写纪律、调试方法、工程约束。**不新增架构范式、不私自分层、不自定义逻辑**。

## 1. 整体架构总纲(核心思想,不可改动)

### 1.1 架构定义
**四文件绝对扁平化架构**,无分层、无分组、无嵌套、无场景子模块、无状态机代码、无业务 if-else 硬编码。

所有设备控制逻辑、联锁、时序、优先级、工况切换,全部由 `rules.json` 单层规则表承载。

### 1.2 四大固定文件(工程永久结构)

```
project/
├── main.py               # 万能固定主控内核 (one for all)
├── source_plugins.py     # 传感器采集小程序集
├── action_plugins.py     # 执行动作小程序集
└── rules.json            # 扁平化业务规则总表
```

**不增架构文件、不减核心文件**。

### 1.3 核心运行机制(冲突规避基石)

- 规则从上到下顺序 = 优先级从高到低
- 单控制周期**仅执行第一条命中规则**
- 命中高优先级规则后,直接终止本轮剩余规则判断,天然杜绝动作冲突
- 安全、保护、急停规则永远置顶,拥有最高抢占权

### 1.4 复杂任务解决方案(禁止分层分组)

所有复杂时序、多工序、多工况、状态流转,**不分组、不分层、不子规则**。

统一解决方案:**上下文状态变量 + 规则条件过滤** 实现软状态机(FSM)。

工序阶段、工况模式全部存放在 `ctx` 业务状态变量,通过规则 `cond` 表达式筛选当前可执行规则。

## 2. 全局上下文 Context 设计规范(线程安全·变量隔离)

### 2.1 变量严格二分(架构铁律)

上下文变量永久分为两类,读写权限严格隔离,跨类禁止乱写:

| 类别 | 写入方 | 读取方 | 备注 |
|------|--------|--------|------|
| **外源传感器变量** (距离/速度/按钮/位置/温度等) | 仅后台IO线程 | 主线程(快照只读) | 业务代码、动作插件禁止修改 |
| **内源业务状态变量** (task_stage / 任务标记 / 工序状态) | 仅主线程 action 动作插件 | 全线程只读 | IO 线程、采集插件禁止修改 |

### 2.2 时间戳变量规范

固定保留 `ts_io` 变量,由IO线程每帧刷新,用于规则层实现:
- 传感器超时检测
- 硬件掉线保护
- 数据新鲜度校验
- 延时逻辑

**禁止使用 `time.sleep` 做业务延时**,全部通过时间戳差值在规则表达式实现。

## 3. 多线程数据同步终极规范(必须严格遵守)

### 3.1 双线程架构固定模型

- **后台IO线程**:独立无限循环,纯硬件采集更新,与规则引擎完全解耦
- **主线程**:规则调度、条件判断、动作执行、状态流转

### 3.2 线程安全标准流程(唯一合法同步方式)

**后台IO线程流程(锁外IO,锁内赋值)**:
1. 锁外执行全部硬件读取、阻塞IO、串口读取、CAN解析
2. 数据存入局部字典缓存(不触碰共享ctx)
3. 加锁,极短临界区批量赋值到共享ctx
4. 解锁、`sleep` 等待下一帧

**主线程流程(快照隔离,杜绝脏读)**:
1. 每周期开始加锁,完整拷贝一份 ctx 快照
2. 解锁,后续所有规则判断全部使用快照数据
3. 仅命中动作时,修改原始ctx的业务状态变量

### 3.3 线程禁止行为(红线)

- 禁止锁内做IO、`sleep`、耗时运算
- 禁止主线程直接读取原始 ctx 做规则判断
- 禁止IO线程修改业务状态变量
- 禁止动作插件修改传感器变量
- 禁止任何插件内部写死业务 if-else 逻辑
- 禁止 `eval` 加载**网络/不可信来源**的 `rules.json` (eval 代码注入风险)

## 4. 四大文件详细开发规范

### 4.1 main.py 主控内核(永久固定,禁止业务修改)

**定位**:通用调度框架,定型后永不写入业务逻辑。

**固定职责**:
- 加载 rules.json 规则表
- 启动独立后台IO线程
- 线程锁、快照拷贝、数据同步
- 单周期优先级抢占调度、冲突规避
- 规则表达式求值、异常捕获

**开发约束**:新增业务、新增工况、新增联锁,**绝不修改 main.py**。

### 4.2 source_plugins.py 传感器采集集

**定位**:纯硬件读取层,无业务、无状态、无逻辑。

**规范**:
- 所有采集函数只读硬件、不写状态、不判断逻辑
- 统一返回局部数值,由IO线程批量刷入ctx
- 新增传感器:写新函数 → 加入 `io_task_all_sensors()` 集合 → `RobotContext` 加字段
- 禁止修改 `task_stage` 等业务状态
- 禁止 `sleep`、禁止延时、禁止阻塞主框架

### 4.3 action_plugins.py 动作执行集

**定位**:硬件执行 + 业务状态切换。

**两类动作严格区分**:
- 硬件执行动作:刹车、前进、夹爪、报警、输出IO
- 状态迁移动作:仅修改 `task_stage`,无硬件输出,用于工序流转

**核心铁律**:所有业务判断、条件筛选、时序逻辑,一律不写在动作代码中,全部交给规则表。

**新增动作**:编写函数 → 注册到 `ACTION_PLUGIN_REGISTRY` 即可。

### 4.4 rules.json 规则总表(唯一业务入口)

**定位**:整机所有业务逻辑、联锁、时序、优先级的**唯一载体**。

**固定精简化字段(永久不扩容、不嵌套、不分组)**:
- `name`:规则名称(可读性、调试溯源)
- `src`:依赖传感器插件列表(文档溯源、编辑器关联,**不执行采集**)
- `cond`:条件表达式(Python 原生语法,支持传感器+状态+时间戳混合判断)
- `act`:命中后执行的动作插件名

**格式规范**:
- 单行紧凑格式,扁平化排列
- 优先级从上至下递减
- **保护类规则置顶,业务规则后置**

## 5. 表格编程开发流程(标准作业程序)

所有新功能开发,严格按照以下顺序执行,**禁止逆向、禁止跳步**:

1. **步骤 1:硬件层适配** — `source_plugins.py` 新增传感器读取函数 + 加入批量采集入口
2. **步骤 2:动作层适配** — `action_plugins.py` 新增执行动作/状态切换函数 + 注册进动作注册表
3. **步骤 3:配置业务逻辑** — 编辑 `rules.json` 增删规则,调整优先级顺序
4. **步骤 4:分层调试** — 先 `io_debug.py` 验证硬件,再 `main.py` 验证业务

## 6. 调试体系规范(分层独立调试)

### 6.1 两层完全隔离调试体系

- **硬件层调试**:`io_debug.py` 独立运行,只测IO采集、线程、数据同步,不跑业务
- **业务层调试**:`main.py` 运行,只测规则逻辑、状态流转、动作执行

**优势**:硬件问题、逻辑问题彻底割裂,精准定位,无互相干扰。

### 6.2 故障排查唯一思路

程序异常**优先看规则表**,其次看 ctx 快照,**最后才看插件代码**:

- 90% 业务 BUG:规则顺序、条件表达式、优先级问题
- 9% 硬件 BUG:采集异常、线程不同步
- 1% 代码 BUG:插件编写不规范

## 7. 架构永久禁止项(红线约束)

以下行为**永久禁止**,任何迭代不得突破:

- 禁止规则分组、分层、子规则、场景嵌套
- 禁止在 main.py 写入任何业务逻辑、判断、工况
- 禁止在插件内写业务 if-else 判断
- 禁止动作插件并发执行(依靠单周期单规则机制永久互斥)
- 禁止使用 `sleep` 做业务延时
- 禁止跨线程乱写变量
- 禁止废弃扁平化结构、回归传统硬编码流程
- 禁止加载网络/不可信来源的 `rules.json` (eval 注入风险)

## 8. 架构核心优势(设计初衷总结)

- **极高可读性**:看懂 `rules.json` 即看懂整机程序,无需通读代码
- **极强可维护性**:改业务只改配置,不动内核代码
- **零冲突机制**:天然优先级抢占,彻底解决动作互斥
- **软硬解耦**:硬件采集独立线程,业务规则纯配置,互不阻塞
- **零代码业务迭代**:配合可视化编辑器,现场零代码调试设备逻辑
- **标准化可传承**:固定四文件结构、固定开发范式、固定调试流程,团队统一标准
